# L1 evidence: first long-horizon dogfood run (2026-09-07)

Protocol: `docs/dogfood/L1/README.md`. One session of real Keel in `ask`
mode on the `tally` repository with Qwen3.6. Reported by the user; raw
material below is verbatim except where the lab or the reviewer marks an
elision. Keel and PIRA were not changed during the run.

## Verdict

**L1 failed.** Hidden acceptance 0/7. The project's own suite went from 13
passing to 11 collected with one import error, because `tally/cli.py` was
overwritten with the literal `test` and never restored. README unchanged, no
tests added. The only correct change that landed was the thousands-separator
fix in `records.py`. Session: 21:41:24Z to 21:54:22Z (12 min 58 s); three
`Continue` messages used; the model never declared completion and never
asked a question.

The run exposes one dominant harness limitation and several secondary ones.
The dominant one: **Keel gives the model no reliable way to write a
multi-line file.** With an argv-only shell on Windows, every file body must
travel inside one quoted argument; 28 of 42 tool calls were spent trying to
write a 45-line `cli.py` by seven different shell tricks, none succeeded,
and one "writability test" destroyed the file. No mechanism is selected in
this report; see "Candidates, not decisions".

## Observations by category

Attribution follows PLAN §2 ("own the instruction path"): what Keel
contributed is stated before what the model did. Call ids refer to the
session log.

### 1. Unreliable shell editing (dominant; harness)

- **What Keel provides.** One tool, `shell`, with an `argv` array executed
  without a shell. Writing a file therefore means either a shell built-in
  through `cmd /C "…"` / `powershell -Command "…"`, or an interpreter
  one-liner (`python -c "…"`), with the entire file body inside one argument
  and quoted for that interpreter, then again as a JSON string. There is no
  stdin path (the process gets `Stdio::null()`, so `python -` printed the
  interactive banner and exited, call `a4dcb34d`, exit 0, which the model
  read as success).
- **What happened.** Navigation and understanding took 10 calls in 2 turns
  and were flawless. Then `records.py` (67 lines) was rewritten successfully
  on the fourth attempt with `python -c "open(…).write('''…''')"`
  (`a5fa6747`), the only working recipe of the session. `cli.py` (45 lines,
  containing single quotes, double quotes, f-strings with braces, and
  backslashes) was then attempted 28 times (23 executed, 5 refused as
  malformed) by seven strategies: `python -c` triple quotes (SyntaxError on
  escaping, `b84d6c18`, `b05deef4`, `af5e3567`), PowerShell here-string
  (refused), `cmd echo` redirection line by line (some lines failed on
  metacharacters, `944247ca`), a patch script assembled in pieces in `%TEMP%`
  and in the repository (`patch_cli.py`, `tally_patch.py`, never complete),
  base64 (`a3eac23c` produced the string; `pira_ctx` clipped 1553 bytes of it
  in the synopsis, and the next step never decoded it), `python -` via stdin
  (impossible under Keel), and a bare "writability test" that wrote `test`
  into `cli.py` (`a36cd69c`) and was never followed by the real content.
  README and tests were never reached.
- **Evidence weight.** 28/42 calls, 0 successes, one destroyed file. This is
  a harness limitation: the model's content was correct at least twice (the
  refused payloads `815de924` and `982d032d` contain a plausible complete
  `cli.py` with `--month` and `MONTH_RE`); the channel, not the content,
  failed.

### 2. Malformed tool calls (8/42; model or serving stack, surfaced correctly by Keel)

- Every long payload (whole-file writes, long PowerShell commands) arrived
  with `argv` as one JSON **string** rather than an array; in five of them
  the string contains the whole arguments object, `intent`, `effect` and
  `safety_review` included (`8e58511e`, `b9449825`, `815de924`, `bdf4da0d`,
  `982d032d`; also `af9c1603`, `9f6b5db9`, `a38d2b0c`). Short calls were
  always well-formed.
- Keel refused all eight before approval, with no handshake, no `Safety:`,
  and the observation `not executed: input needs an array field 'argv'`
  (T15 final-patch behavior, now confirmed under load).
- The model did not identify the cause. It concluded "the shell tool is
  rejecting longer commands" and switched to fragmenting the content, which
  fed observation 1.
- Not determinable from the log: whether the model generated the collapsed
  string or vLLM's tool-call parser produced it from otherwise valid
  output. Discriminating check for a later run: compare the raw
  `tool_calls[0].function.arguments` in the wire capture with the model's
  reasoning text for the same response, or serve the same model with a
  different tool parser.

### 3. Silent turn endings (3 of 4 runs; harness and model)

- Runs 2, 3 and 4 ended with an assistant message that had no text and no
  tool calls (`finish_reason = stop`, completion 172 / 171 / 191 tokens, all
  of it reasoning stripped by the server's reasoning parser). Keel treats a
  message without tool calls as the final answer, so the run ended and the
  REPL printed only `> `. Each cost one of the three `Continue` messages.
- The model never declared completion and never asked anything. Whether the
  stripped reasoning contained a plan or a question is visible only in the
  wire capture (local).
- Harness side: the loop has no notion of an empty final answer; the REPL
  gives the user no signal that the model produced nothing.

### 4. Provider timeout without recovery (1 run; harness)

- Request 3 of run 1 (14 messages, ~10.4k prompt tokens, the first request
  carrying nine tool results) did not return within Keel's fixed
  `REQUEST_TIMEOUT` of 300 s. The run aborted with `model provider error`,
  the transcript kept the user turn, the assistant's nine calls and their
  results, and the same content succeeded in 6 s after `Continue`. There is
  no retry (a recorded decision), and the client cannot tell a stuck server
  from a long generation; the wire recorded only `response_error`.

### 5. Failure recovery (model)

- Repeated the same failing strategy (three `python -c` writes of `cli.py`
  failed on escaping; three separate patch-script assemblies were started
  and abandoned).
- Ran a script it had never successfully written (`94654542`, 21:48:32,
  `%TEMP%\tally_patch.py`: "can't open file"), that is, it believed an
  earlier refused call had executed.
- Read the Python REPL banner as success (`a4dcb34d`).
- Never re-ran the test suite after the first edit; never checked `cli.py`
  after the destructive write.

### 6. Permission friction (harness)

- 42 prompts in 13 minutes. Prompts for `python -c` payloads run to several
  kilobytes of doubly escaped text; a person cannot review them. When a
  turn carried several calls, the prompts printed back to back with each
  `approve? …` starting on the same line as the previous `[y/N] `, because
  the answer is not echoed when stdin is piped. `ask` mode as built is not
  usable by a human at this call rate and payload size; the operator
  replaced it with a driver, which is itself a finding.

### 7. Memory usefulness (neutral)

- `pira_ctx` recorded every executed command with a clear intent (34 rows).
  The model used no memory tool (`history`, `pira_dec`, workbook) and needed
  none in 13 minutes. No evidence either way yet.

### 8. Context (no degradation observed)

- Prompt grew 6.1k → 27.8k tokens over 37 calls, 697k prompt tokens in
  total. No forgetting of the task or of file contents was observed; the one
  false belief (observation 5, the phantom temp script) is a failed-action
  bookkeeping error, not context loss.

### 9. Navigation (good)

- 10 reads in 2 turns covered every relevant file, using `cmd /C type`
  correctly this time (the `type`-as-program mistake of the T15 sessions did
  not recur).

### 10. Other harness observations

- The REPL has no multi-line input; the task text had to be flattened to one
  line.
- `session_stats.py` (dogfood tooling) crashed on a `run_end` carrying
  `error` instead of `turns`.
- The protocol asked for `pira_ctx history --limit 200`; the cap is 100.
- The `--trace` output shows an empty assistant message as `[assistant]`
  followed by two blank lines.

### 11. PIRA compliance (model)

- Temporary scripts went to `%TEMP%` (PIRA-compliant) and also into the
  repository root (`patch_cli.py`, `tally_patch.py`), and were left behind.
- Every state-changing call carried a `safety_review` (19/19), so the
  handshake held; the reviews were templated ("Safe, no risk"), including
  the one for overwriting `cli.py` with `test` (`a36cd69c`: "Test only —
  just writing 'test' to verify file is writable"), which is the layer Keel
  by decision does not own.
- `records.py` was written back with CRLF (`python -c` on Windows, text
  mode), producing a Git line-ending warning.

## Candidates, not decisions

Listed with the evidence each would answer; none is selected here.

| Candidate | Evidence in L1 | What it would not fix |
|---|---|---|
| A structured file write/edit tool (path + content or replacement) | Observation 1: 28 calls, 0 successes, destroyed file; observation 2 partly (long payloads would still be long, but no interpreter quoting) | Model serialization collapse on long arguments (observation 2), if that is the model's |
| Stdin for `shell` (feed the content, run `python -`) | Observation 1 (the model reached for `python -` on its own); keeps "everything through `pira_ctx`" intact | Quoting inside the content is gone, but the payload still rides one JSON string |
| Explicit handling of an empty final answer (e.g. surface it as such; the user decides) | Observation 3: 3 of 4 runs | Why the model stopped |
| Timeout policy (longer, per-request, or one retry on timeout) | Observation 4 | Diagnosis of the server side |
| Approval prompt rendering (compact summary, echo, one prompt per line) | Observation 6 | The rate of prompts itself |
| Multi-line REPL input | Observation 10 | — |

A harder workload is not the next step: L1 did not pass, and the failure is
concrete.

## Protocol corrections made after this run

- `docs/dogfood/L1/tools/session_stats.py` tolerates `run_end` events that
  carry `error` and reports them.
- The procedure uses `pira_ctx history … --limit 100` (the tool's cap).
- Operator rule 4 now follows PIRA's boundary: decline a command acting
  outside the repository **and outside the platform temp directory**.

The frozen task text, seed, and acceptance tests are unchanged.
