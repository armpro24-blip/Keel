## What this decides

1. **Identity transfer works.** `AGENTS.md` verbatim as system instruction is
   enough for a 119B local model to identify as PIRA, quote the token, and
   apply the host block (approval mode) to PIRA's own rules.
2. **The loader is used as designed.** The model routes through
   `read_pira_policy` rather than any shell path, batches independent loads
   in one turn, and does not re-load already loaded modules (probe 6).
3. **Schema-level constraint prevents undeclared loads before they happen.**
   The `enum` of declared names stopped the model from even attempting
   `AGENTS`. The loader's runtime rejection remains the backstop.
4. **Routing fidelity is the model's, not Keel's.** Loading `explain` for a
   debugging task is over-inclusion relative to PIRA master's routing text.
   Keel preserves PIRA's design of leaving routing to the model; this
   observation belongs to PIRA's routing evaluation, not to Keel's contract.
5. **Context cost is acceptable.** After probe 2 the context held
   `AGENTS.md` plus three modules (roughly 45 KB of policy) and the run
   stayed fast (17 s for six probes).

## Consequences for slice C

- Batched tool calls will include shell commands; sequential execution and
  the `pira_ctx` single-live-capture assumption apply from the first run.
- The model already knows the `Safety:` rule for full mode. Slice C's `ask`
  mode must be reported in the host block so the model does not print
  reviews the host will ask about anyway (PLAN.md §8 T6).
- `pira_ctx` 1.9.0 changed CLI forms (`range START:END`, `search --limit`,
  `list --live`); Keel wraps commands and does not parse these, so no change
  is needed, but `pira.lock` will report the tool drift on machines still on
  1.8.0.

## Limits of this evidence

One model, one server, one run, six probes. It does not show how the model
behaves when the loaded policy conflicts with a user request, nor how it
handles shell output as untrusted data; both are slice C questions.
