## What this decides for M2

1. **Batched tool calls are real.** The model emitted three calls in one turn.
   Keel's sequential, declaration-order execution (PLAN.md §5.3) will be
   exercised from day one; the `pira_ctx` single-live-capture assumption
   that motivates it matters in practice.
2. **Structured arguments are reliable.** Every `arguments` string parsed as
   JSON. The M2 `shell` schema can require `argv: Vec<String>` plus `intent`
   without a fallback path for malformed input; malformed input stays a
   visible error as designed.
3. **Context budget is comfortable.** `max_model_len` is 65536 tokens. PIRA
   `master` `AGENTS.md` is about 24 KB (roughly 6–7k tokens), so loading it
   verbatim every turn is affordable; compaction (M4) is not urgent for this
   deployment.
4. **Latency is low.** Five model calls in about 6 s. Synchronous HTTP without
   streaming is not a usability problem here.

## Limits of this evidence

One model, one server, one run, four probes. It shows this deployment
supports Keel's tool protocol; it does not show that every OpenAI-compatible
server does, nor how the model follows a long policy text such as PIRA's
`AGENTS.md`. That second question is what M2 will observe.
